# Evidence-based project reviews

Use these lenses when a review or audit is requested; they are investigation aids, not standing tasks or extra verification gates. Scope the review to the request. A full review should cover its stated areas and representative important flows, including unchanged code; say what was sampled or unavailable. Finding no confirmed issues is a valid result.

For each candidate, establish the intended behavior from the current owner, trace the reachable path and consumers, and look for counterevidence such as an intentional variant, validation at another boundary or compatibility needs. A search hit, large file, passing test or suspicious pattern alone is not a finding. Explain the concrete failure or maintenance cost, impact, confidence and remedy; distinguish leads from confirmed issues. Prioritize data loss and blocked or incorrect play before cosmetic or speculative concerns. Keep related causes and fixes together, preserve intentional behavior, and do not weaken diagnostics to make a review pass.

| Lens                       | Questions and project starting points                                                                                                                                                                                                                                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime and recovery       | Trace action → validation → mutation → persistence → feedback → reload. Can repetition, interruption, a rejected command or a stale completion lose progress or strand a phase? Check `src/lib/game/session.ts`, `run.ts`, `run-save.ts`, `src/lib/save/` and `desktop/save.cjs`; compare uninterrupted and resumed behavior where relevant. |
| Side effects and ownership | Who owns RNG, storage, timers, subscriptions, browser APIs and teardown? Trace lifetime and failure handling through actual consumers before introducing another adapter. Preserve command-bound gameplay randomness and the distinct browser and desktop save boundaries in [architecture](ARCHITECTURE.md).                                |
| Tests                      | Map important failure modes to assertions. What plausible broken behavior would still pass? Investigate flakes at the relevant ordering and layer; preserve useful distinct coverage instead of optimizing for test count. [Contributing](../CONTRIBUTING.md) owns check selection.                                                          |
| UI and interaction         | Follow entry, action, feedback, cancellation and completion with relevant pointer and keyboard flows. Check focus, names, states, sizing and settings; inspect visual changes in the renderer as described in [UI](UI.md). A different token or layout is a lead only when it has a visible, semantic or maintenance cost.                   |
| Documentation              | Walk a real task from its entry point and verify commands, prerequisites, paths, links and recovery guidance against source. Keep one owner for durable policy and preserve historical evidence with its limits; see the [design index](README.md).                                                                                          |
| Simplification and types   | Confirm actual unused consumers, duplicated responsibility, dishonest types or a recurring change cost before deleting or consolidating. Generated data, composition roots, validation boundaries and compatibility paths may be intentional. Check callers, schemas, tests and generated sources when changing ownership.                   |
| Performance                | Establish a material cost with a reproducible workload or a provable resource issue. Record revision, build mode, scenario, viewport and measurement conditions; compare equivalent work and report variation. Fewer renders or a smaller file alone do not prove a player-visible improvement. Preserve presentation and seeded outcomes.   |

Verify the behavior affected by a confirmed remedy at the appropriate layer and report checks actually run, remaining confirmed issues and material uncertainty. An unavailable check limits the conclusion; it does not erase other evidence. Keep lasting rules in their existing owner rather than storing completed review ledgers here.
